"PHP 취약점으로 셸을 딴다"는 말을 많이 듣지만, 정작 **그 한 번의 요청이 어떻게 서버 명령 실행으로 이어지는지**는 흐릿하게 아는 경우가 많다.

이 글은 그 과정을 **말이 아니라 격리된 샌드박스에서 직접 재현**해 보여준다. Docker 컨테이너(`php:8.3-apache`) 안에 일부러 취약한 PHP를 띄우고, ① **명령 주입(Command Injection)** 과 ② **웹셸 업로드(File Upload → Webshell)** 두 경로로 실제 서버 명령을 실행시킨 뒤, 그 공격을 **막는 코드가 정말 막는지**까지 검증한다. 아래 모든 출력·화면은 **직접 실행한 실제 결과**다.

> ⚠️ 모든 실습은 **로컬에서만 접근되는 격리 컨테이너(localhost)** 에서 수행했다. 취약 코드를 실제 서버·공개망에 올리지 말 것. 이 글의 목적은 **원리 이해와 방어**다.

## 취약점은 왜 생기는가 — "데이터가 코드가 되는 순간"

웹 애플리케이션의 거의 모든 심각한 취약점은 한 문장으로 요약된다. **신뢰할 수 없는 사용자 입력(데이터)이, 어딘가에서 코드·명령(실행)으로 해석되는 것.** PHP에서 이 "데이터 → 실행" 경로는 대표적으로 두 가지다.

**① 입력이 OS 셸 명령으로 흘러갈 때 (Command Injection)**

PHP는 `system()`, `exec()`, `shell_exec()`, `passthru()`, 백틱(`` ` ``) 등으로 OS 명령을 실행할 수 있다. 여기에 사용자 입력이 **검증 없이** 들어가면, 공격자의 문자열이 그대로 서버 셸에서 실행된다.

```php
// 이 한 줄이 원격 코드 실행(RCE)의 전부다
system($_GET['cmd']);
```

**② 입력이 PHP 파일로 저장·실행될 때 (Webshell)**

PHP는 "웹 루트에 있는 `.php` 파일 = 실행할 코드"다. 업로드를 제대로 검증하지 않으면, 공격자가 `shell.php`를 올리는 순간 그 파일은 **서버에서 실행 가능한 코드**가 된다. 이것이 "PHP2Shell"의 가장 전형적인 모습이다.

```php
// 올라온 파일을 이름 그대로 웹 루트에 저장 → 올린 .php가 실행된다
move_uploaded_file($_FILES['f']['tmp_name'], "uploads/" . $_FILES['f']['name']);
```

두 경우 모두 근본 원인은 같다. **입력을 데이터로만 다뤄야 하는데, 실행 가능한 맥락(셸·파일 시스템)에 그대로 넘긴 것.**

## 샌드박스 구성

격리를 위해 Docker 컨테이너로 취약 환경을 만들었다.

```bash
# php:8.3-apache 컨테이너에 취약 PHP를 올리고 localhost:8099 로만 노출
docker run -d --name php2shell -p 8099:80 \
  -v ./php2shell:/var/www/html php:8.3-apache
```

웹 루트(`/var/www/html`)에 둔 파일은 네 개다.

| 파일 | 성격 | 역할 |
| --- | --- | --- |
| `cmd.php` | 취약 | `system($_GET['cmd'])` — 명령 주입 |
| `upload.php` | 취약 | 확장자 검증 없는 업로더 |
| `secure_cmd.php` | 안전 | 허용목록으로 명령 고정 |
| `secure_upload.php` | 안전 | 확장자 허용목록 + 난수 파일명 |

## 검증 ① 명령 주입 (Command Injection → RCE)

취약한 `cmd.php`는 `cmd` 파라미터를 그대로 `system()`에 넘긴다. 브라우저에서 `?cmd=id;uname -a` 를 주면, 서버가 그대로 실행해 결과를 돌려준다.

![cmd.php에 id;uname -a를 주입하자 www-data 권한으로 명령이 실행된 화면](/images/php2shell-2-cmd-rce.jpg)

```text
GET /cmd.php?cmd=id          → uid=33(www-data) gid=33(www-data) groups=33(www-data)
GET /cmd.php?cmd=uname -a    → Linux ... 6.18.x x86_64 GNU/Linux
GET /cmd.php?cmd=whoami; head -n 3 /etc/passwd
  → www-data
    root:x:0:0:root:/root:/bin/bash
    daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
```

**요청 한 번으로 서버에서 임의 명령이 실행됐다.** `;` 로 명령을 이어 붙이면(`whoami; cat ...`) 연쇄 실행도 된다. 이 시점에서 공격자는 사실상 **웹 서버 권한(`www-data`)의 셸**을 쥔 것과 같다.

## 검증 ② 웹셸 업로드 (File Upload → Webshell)

더 지속적인 공격은 **웹셸을 심는 것**이다. `upload.php`는 확장자를 검증하지 않으므로, 공격자는 아래 같은 `shell.php`를 업로드한다.

![확장자 검증이 없는 취약한 업로드 폼](/images/php2shell-1-upload.jpg)

```php
<?php system($_GET['c']); ?>   // 공격자가 올리는 웹셸의 핵심
```

```text
POST /upload.php  (f=@shell.php)   → uploaded: uploads/shell.php
```

업로드가 끝나면 그 파일은 웹에서 접근 가능한 `uploads/shell.php`가 되고, **열 때마다 서버 명령을 실행하는 상시 백도어**가 된다.

![업로드된 uploads/shell.php가 id·whoami·ls를 실행해 웹 루트를 나열한 화면](/images/php2shell-3-webshell.jpg)

```text
GET /uploads/shell.php?c=id                       → uid=33(www-data) ...
GET /uploads/shell.php?c=whoami;ls /var/www/html  → www-data
                                                     cmd.php  secure_cmd.php
                                                     secure_upload.php  upload.php  uploads
```

명령 주입이 "그 순간의 실행"이라면, 웹셸은 **언제든 다시 들어올 수 있는 영구 통로**라는 점에서 더 위험하다. 이것이 PHP2Shell의 핵심 시나리오다.

## 검증 ③ 해결 방안 — 막는 코드는 정말 막는가

방어의 원칙은 하나다. **입력을 실행 맥락에 그대로 넣지 않는다.** 두 취약점에 각각 대응한다.

### 명령 주입 방어 — 셸에 문자열을 넘기지 않는다

가장 확실한 방법은 **애초에 사용자 문자열로 명령을 만들지 않는 것**이다. 꼭 외부 명령이 필요하면 **실행할 명령을 허용목록으로 고정**하고, 인자는 `escapeshellarg()`로 격리한다.

```php
$allow = ['date', 'uptime', 'whoami'];        // 허용된 명령만
$cmd   = $_GET['cmd'] ?? '';
if (!in_array($cmd, $allow, true)) {          // 목록 밖이면 차단
    http_response_code(400);
    exit('blocked');
}
system($cmd);                                  // 고정된 명령만 실행
```

허용목록 밖인 `id`는 **차단(HTTP 400)**, 안에 있는 `whoami`만 통과한다.

![secure_cmd.php가 허용목록 밖 명령 id를 HTTP 400으로 차단한 화면](/images/php2shell-4-secure-block.jpg)

```text
GET /secure_cmd.php?cmd=id;cat /etc/passwd   → blocked        [HTTP 400]
GET /secure_cmd.php?cmd=whoami               → www-data       [HTTP 200]
```

### 업로드 방어 — 실행 가능한 파일을 못 올리게, 올려도 실행 못 하게

업로드 방어는 **다층(defense in depth)** 이 핵심이다.

1. **확장자 허용목록**(화이트리스트) — `jpg/png/gif`만 허용, `.php`는 거부
2. **파일명을 서버가 난수로 결정** — 공격자가 경로·이름을 못 정함
3. **웹 루트 밖(또는 실행 차단된 폴더)에 저장** — 올려도 PHP로 실행 안 됨
4. 추가로 업로드 폴더에서 PHP 실행 비활성화(Apache `php_admin_flag engine off` / Nginx 위치 차단), `disable_functions`로 `system,exec,...` 봉쇄

아래는 1·2를 구현한 `secure_upload.php`다.

```php
$allowExt = ['jpg', 'jpeg', 'png', 'gif'];
$ext = strtolower(pathinfo($_FILES['f']['name'], PATHINFO_EXTENSION));
if (!in_array($ext, $allowExt, true)) {
    http_response_code(400);
    exit("blocked: .$ext 는 허용되지 않습니다");
}
$safe = bin2hex(random_bytes(8)) . "." . $ext;   // 난수 파일명
move_uploaded_file($_FILES['f']['tmp_name'], "uploads/$safe");
```

같은 `shell.php`를 올리면 **거부**되고, 정상 이미지는 **난수 이름**으로만 저장된다.

```text
POST /secure_upload.php  (f=@shell.php)   → blocked: .php 는 허용되지 않습니다
POST /secure_upload.php  (f=@pic.gif)     → ok: uploads/eb009c0bd0554d02.gif
```

> 확장자 검사만으로는 `shell.php.jpg`, 이미지에 PHP를 숨긴 폴리글랏, `.phtml`·`.phar` 같은 우회가 남는다. 그래서 **"업로드 폴더에서는 PHP를 아예 실행하지 않는다"** 는 서버 설정이 마지막 안전장치로 꼭 필요하다. 허용목록·난수명·실행차단을 **함께** 써야 한다.

## 정리

| | 취약 (Before) | 안전 (After) |
| --- | --- | --- |
| 명령 실행 | `system($_GET['cmd'])` → 임의 RCE | 허용목록 고정 → 목록 밖 차단(400) |
| 파일 업로드 | 이름 그대로 저장 → `.php` 웹셸 | 확장자 화이트리스트 + 난수명 + 실행차단 |
| 공통 원인 | **입력이 실행 맥락으로 흘러감** | **입력을 데이터로만 취급** |

- PHP2Shell은 마법이 아니다. **사용자 입력이 `system()`류 함수나 `.php` 저장 경로에 검증 없이 닿는 순간**, 웹 요청 하나가 서버 셸이 된다. 샌드박스에서 `id` 한 번으로 `www-data` 권한이 그대로 드러났다.
- 방어의 핵심은 기능 추가가 아니라 **경계 긋기**다. 셸에는 사용자 문자열을 넘기지 말고(허용목록·`escapeshellarg`), 업로드는 화이트리스트·난수명·실행차단을 **겹쳐서** 막는다.
- 코드 리뷰에서 `system`·`exec`·`shell_exec`·`eval`·`move_uploaded_file`·`include($_...)` 가 **사용자 입력과 만나는 지점**을 먼저 의심하자. 거기가 대부분의 PHP2Shell이 시작되는 자리다.
