[webhacking.kr](https://webhacking.kr)의 **old-23** 문제를 풀었다.
목표가 대놓고 적혀 있다 — **`<script>alert(1);</script>`를 그대로 주입하라.**
그런데 이 문자열을 넣으면 서버가 `no hack`을 뱉는다. 필터가 있다는 뜻이다.

핵심은 **필터가 문자열을 세는 방식과, 서버가 그 문자열을 출력하는 방식이 다르다** 는 점이다.
그 틈을 **널 바이트(`%00`)** 한 줌으로 비집고 들어가 `alert(1)`을 띄운다.

이 글은 추측이 아니라 **실제로 서버에 값을 넣어 가며 필터 규칙을 역추적하고, 우회 페이로드로 통과(`Pwned`)를 확인** 한 과정을 그대로 정리한다.

## 1. 문제 개요

| 항목 | 값 |
| --- | --- |
| 사이트 | webhacking.kr (old) |
| 문제 | old-23 (`/challenge/bonus-3/`) |
| 배점 | 20점 |
| 유형 | XSS / 필터 우회 (null byte) |
| 목표 | `<script>alert(1);</script>` 주입 |

화면에는 입력창 하나와 안내문뿐이다.

```html
<form method=get action=index.php>
  <input name=code> <input type=submit>
</form>
Your mission is to inject <script>alert(1);</script>
```

`code` 파라미터를 GET으로 보낸다. 안내대로 `<script>alert(1);</script>`를 그대로 넣어 보면,

```text
GET /challenge/bonus-3/index.php?code=<script>alert(1);</script>
→ 본문에 "no hack"
```

주입은 반사되지 않고 **`no hack`** 만 돌아온다. 소스는 공개되지 않으니(`index.phps`는 403, `?view-source`도 막혀 있다), **입력을 바꿔 가며 필터의 규칙을 알아내야 한다.**

## 2. 정보 수집 — 필터 규칙 역추적

여러 입력을 넣어 `no hack`이 뜨는지(차단) 아닌지(통과)를 비교했다. 아래는 **전부 서버가 실제로 보여 준 결과** 다.

| 입력 `code` | 결과 |
| --- | --- |
| `a` | 통과 |
| `aa` | **no hack** |
| `ab` | **no hack** |
| `abc123` | **no hack** |
| `alert(1)` | **no hack** |
| `<script>` | **no hack** |
| `a b` (사이 공백) | 통과 |
| `<b>` | 통과 |
| `<x>y</x>` | 통과 |
| `1a` / `a1` | 통과 |
| `a_` / `_a` | 통과 |
| `a-b` / `a.b` / `a<b` | 통과 |

규칙이 선명하게 드러난다.

- `aa`·`ab`·`script`·`alert`처럼 **영문자가 두 글자 연속** 이면 차단된다.
- 반대로 `1a`·`a1`·`a_`·`a-b`는 통과한다 — **숫자·기호·언더스코어는 "글자"로 치지 않는다.**
- 글자 사이에 **글자가 아닌 문자가 하나라도 끼면** 연속이 끊겨 통과한다(`a b`, `a.b` …).

즉 필터는 대략 이런 모양이다.

```php
// 관찰된 동작으로부터 복원한 의사 코드 (서버 소스는 비공개)
if (preg_match("/[a-z][a-z]/i", $_GET['code'])) {
  exit("no hack");          // 연속된 영문자 2글자가 있으면 차단
}
```

`<script>alert(1);</script>`는 `script`·`alert` 같은 **연속 글자 덩어리** 로 가득하니 당연히 걸린다.
그렇다면 **글자 사이를 "글자가 아닌 무언가"로 끊되, 브라우저에는 안 보이게** 만들면 된다.

## 3. 문제점 — 필터가 세는 문자열 ≠ 브라우저가 받는 문자열

여기서 결정적인 관찰이 하나 더 있다. 널 바이트(`\x00`, `%00`)를 글자 사이에 끼워 보냈더니,

- **필터 입장**: `s`, `\x00`, `c` … 로 보여 **연속된 글자 두 개가 없다** → 통과.
- **서버 출력**: 반사된 HTML을 바이트 단위로 확인하니 **널 바이트가 사라져 있었다.** 즉 서버는 출력(그리고 정답 판정)에서 널을 제거해 버린다.

그래서 브라우저가 최종적으로 받는 본문은 **널이 빠진 멀쩡한** `<script>alert(1);</script>`가 된다.

> 필터는 `s\x00cript`를 "글자가 끊긴 안전한 값"으로 읽고,
> 브라우저는 널이 제거된 `script`를 "실행 가능한 태그"로 읽는다.
> **같은 입력을 두 주체가 다르게 해석** 하는 이 틈이 우회의 본질이다.

널 바이트가 딱 맞는 이유는 두 가지를 동시에 만족하기 때문이다.
① 필터의 `[a-z][a-z]`를 끊는 **"글자가 아닌 문자"** 이고, ② 출력에서 제거되어 **렌더링을 망가뜨리지 않는다.** (`a.b`처럼 눈에 보이는 문자를 끼우면 필터는 통과해도 `scr.ipt`가 되어 태그가 깨진다.)

## 4. 익스플로잇 — 글자 사이에 널 바이트

목표 문자열에서 **연속된 영문자 사이사이에만** 널 바이트를 끼운다.

```text
<script>alert(1);</script>
   └ script, alert, script 의 글자 사이에 %00 삽입

최종 payload (가독용으로 \0 = 널 바이트):
<s\0c\0r\0i\0p\0t>a\0l\0e\0r\0t(1);</s\0c\0r\0i\0p\0t>
```

`>`·`(`·`1`·`)`·`;`·`<`·`/` 주변은 글자 연속이 아니므로 널이 필요 없다.
이 값을 URL 인코딩(`%00` 등)해 `code`로 전송한다.

```js
// 브라우저 콘솔 기준
const NUL = '\x00';
const spread = s => s.split('').join(NUL);          // 글자마다 사이에 널
const payload = '<'+spread('script')+'>'
              + spread('alert')+'(1);</'
              + spread('script')+'>';
location.href = '/challenge/bonus-3/index.php?code=' + encodeURIComponent(payload);
```

필터 점검: 전송된 `code`에는 어디에도 **연속된 영문자 두 개가 없다**(모든 글자 쌍 사이에 널이 있다) → `no hack`을 넘긴다.
출력 점검: 서버가 널을 지우므로 본문에는 `<script>alert(1);</script>`가 그대로 박힌다 → 스크립트가 실행된다.

## 5. 결과

페이로드를 보낸 순간, 반사된 본문에 멀쩡한 스크립트가 들어가고 통과 처리됐다.

```text
<script>alert(1);</script><script>alert('old-23 Pwned!');</script>
<hr>old-23 Pwned. You got 20point. Congratz!<hr>
```

`alert('old-23 Pwned!')`가 뜨고 점수가 올라갔으며, `chall.php`에서도 **`✔️ old-23`** 으로 풀린 것을 확인했다.
(이미 푼 뒤 같은 페이로드를 다시 보내면 `already solved`가 뜬다 — 우회가 반복 재현된다는 뜻이다.)

> 반사된 HTML을 바이트로 확인했을 때 **널 바이트가 하나도 남아 있지 않았다.**
> 필터만 널을 "글자 아님"으로 세고, 출력은 널을 통째로 버린 결과가 정확히 맞아떨어졌다.

## 6. 왜 취약한가 — 그리고 올바른 방어

**(1) 블랙리스트 필터는 "렌더링과 같은 눈"으로 보지 않으면 뚫린다.**
`[a-z][a-z]` 차단은 그럴듯해 보이지만, 브라우저가 무시·제거하는 문자(널 바이트, 그 밖의 제어문자 등)를 고려하지 못한다.
필터가 보는 문자열과 브라우저가 실행하는 문자열이 **다르면** 그 간극이 곧 우회 경로다.

**(2) XSS의 근본 방어는 "차단"이 아니라 "출력 인코딩"이다.**
사용자 입력을 HTML에 넣을 때는 맥락에 맞게 이스케이프해야 한다. 이 문제의 안내문처럼 `<`를 `&lt;`로 바꿔 **데이터로만** 출력하면, 어떤 기발한 우회가 와도 스크립트로 실행되지 않는다.

```php
// 나쁨: 금지 패턴을 나열하고 그대로 echo
if (preg_match("/[a-z][a-z]/i", $code)) exit("no hack");
echo $code;                      // 널 제거 + 블랙리스트의 틈으로 실행됨

// 좋음: 입력은 항상 데이터로. 맥락에 맞게 인코딩해서 출력
echo htmlspecialchars($code, ENT_QUOTES, 'UTF-8');
```

**(3) 입력 정규화와 검증을 먼저, 일관되게.**
널 바이트·제어문자처럼 "보이지 않는" 바이트는 **받는 즉시 제거하거나 거부** 하고, 그 **정규화된 값** 으로만 필터·출력·판정을 수행해야 한다. 필터와 출력이 서로 다른 버전의 문자열을 보게 두는 순간 방어는 무너진다.

## 7. 정리

- old-23 필터는 **연속된 영문자 두 글자**(`[a-z][a-z]`)를 `no hack`으로 막는다 — 숫자·기호·널은 "글자"로 치지 않는다.
- **널 바이트(`%00`)** 를 글자 사이에 끼우면 필터는 연속이 끊겼다고 보지만, **서버는 출력에서 널을 제거** 해 브라우저엔 멀쩡한 `<script>alert(1);</script>`가 전달된다 → `alert(1)` 실행, 통과.
- 교훈: **블랙리스트는 렌더링과 다른 눈으로 보면 뚫린다.** XSS는 금지 목록이 아니라 **출력 인코딩(`htmlspecialchars`)** 과 **일관된 입력 정규화** 로 막아야 한다.

> "필터가 보는 문자열과 브라우저가 실행하는 문자열이 정말 같은가"를 먼저 묻는다.
> 둘이 갈라지는 순간, 보이지 않는 바이트 한 줌이 `<script>`를 되살린다.
